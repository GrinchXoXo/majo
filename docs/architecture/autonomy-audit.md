# Autonomy audit: every operator dependency (pre-correction baseline)

Audited 7 Oct 2026 against commit `6f11ab1` (Phase 4B), before the 4C autonomous
runtime correction. Each row was verified in code, not taken from reports.

| # | Workflow | Current behaviour (verified) | Why manual | Desired autonomous behaviour | Existing component | Change required |
|---|---|---|---|---|---|---|
| 1 | Typed request → confirmation | `RunExtraction` always ends in `NEEDS_REVIEW` (`request/service.go`); nothing advances until `POST /api/requests/{id}/confirm` | Phase 3.1 §3A-2: offers are delivered automatically, so an unreviewed request must not reach vendors; "No auto-confirm was introduced" | Clear request (product known, location known or derivable from context) → `CONFIRMED` by SYSTEM; otherwise a clarification question | `request.Service.ConfirmAs`, `BuyerRequest.EnsureConfirmed` | New `workflow` policy after extraction; flag `AUTO_CONFIRM_CLEAR_REQUESTS` |
| 2 | Discovery "Ask about it" → confirmation | Created `NEEDS_REVIEW`; auto-confirm only if `DISCOVERY_ENQUIRY_CONFIRMATION=auto` (default `operator`) | Lock §O-1 left it as an open decision | Always clear (fields come from a curated listing) → SYSTEM confirm | `distribution.applyAsk` | Same confirmation policy; the old knob is superseded |
| 3 | Clarification | `POST /api/requests/{id}/clarify` only (operator). `ClarificationSent` actor = OPERATOR | PRD 1 §28 "intentionally simple" | MAJO asks the one question needed for the next action, waits, merges the answer | `request.Service.Clarify`, `defaultClarificationQuestion` | Clarification state + automatic questions; flag `AUTO_CLARIFY_REQUESTS` |
| 4 | Buyer's answer to a question | **Becomes a new BuyerRequest** (`resolver.go`: every non-selection text is `NEW_REQUEST`). `FindLatestOpenByConversation` exists but is never called | Never wired (Phase 3.1 audit §16: "the answer is lost") | Answer merges into the open request, which is re-evaluated | `ContextResolver`, `request.Repository` | Context builder + open-clarification precedence |
| 5 | Referential text ("that phone", "the black one", "something cheaper") | Treated as a new free-text request; extraction finds no product → `NEEDS_REVIEW` | No context layer beyond offer ordinals | Resolve against recent offers / discovery listings / requests; answer, enquire, or ask "which one?" | `ContextResolver` (offers only) | Deterministic context resolution over conversation, offers, discovery deliveries, listings |
| 6 | Matching | `GET /api/requests/{id}/matches` → `SuggestVendors` ("returns ranked candidates for operator review") | PRD 2: matching only suggests | Runs automatically on confirmation | `routing.SuggestVendors`, `matching.Match` | Called by the workflow |
| 7 | Vendor routing | `POST /api/requests/{id}/route` with operator-chosen vendor IDs. Comment: "Never called automatically". `VENDORS_ROUTED` hard-codes actor OPERATOR | PRD 2 §29-33 operator approval | Routing policy: discovery → the listing's vendor; typed → top-N candidates over a score threshold, eligible evidence, vendor open-request limit, no duplicates; "no local vendor" → ask buyer to broaden | `routing.RouteToVendors` | Routing policy + actor-aware `RouteAs`; flags `AUTO_ROUTE_DISCOVERY_REQUESTS`, `AUTO_ROUTE_MATCHED_REQUESTS` |
| 8 | No match | Operator sees an empty match list; buyer hears nothing | Nothing automatic after confirmation | Tell the buyer honestly, or offer a broader search (yes/no question) | — | Workflow no-match policy |
| 9 | Vendor reply association | MM ref → single active → **unmatched queue** (operator `POST /vendor-responses/{id}/associate`). WhatsApp quoted-reply context is not parsed at all | PRD 2.1 §4 "DO NOT AUTO-ASSOCIATE" | 1 structured (MM ref / quoted message) → 2 pending vendor clarification → 3 single active → 4 product match among active → 5 ask vendor "which request?" → 6 exception | `routing.ProcessVendorMessageFrom` | Parse `context.id`; semantic disambiguation; vendor clarification; flag `AUTO_RESOLVE_VENDOR_CONTEXT` |
| 10 | Stale vendor requests | `SENT` forever (`EXPIRED` status exists, never set) → permanent ambiguity for that vendor | Not implemented | Requests older than a TTL stop counting as active | `RoutingRepository.ListActiveByVendor` | `VENDOR_REQUEST_TTL` |
| 11 | Unclear vendor reply ("Which one?", "620k", "maybe") | `UNCLASSIFIED` + `NEEDS_REVIEW` → no offer until operator `PATCH /vendor-responses/{id}` | PRD 2.1 §2: never guess availability | Ask the vendor a targeted question with the request context; the answer becomes the response | `processAsVendorResponse` | Vendor clarification; flag `AUTO_CLARIFY_VENDOR_RESPONSES` |
| 12 | Offer creation + delivery | **Automatic** on each vendor response (`OfferDelivery.VendorResponseChanged`) | — | Unchanged | `marketplace.OfferDelivery` | None (actor stays SYSTEM) |
| 13 | Offer delivery failure | Offers returned to deliverable; retried only by the next vendor reply or operator `POST /offers/deliver` | No retry mechanism | Retry with backoff on the durable job table; permanent / exhausted → exception | `jobs` (Postgres durable jobs) | Retry jobs; flag `AUTO_RETRY_DELIVERY` |
| 14 | Vendor request send failure | `SEND_FAILED`, no retry | Phase 3.1 made failure visible, not recoverable | Retry transient failures; 24h-window (131047) = policy rejection → exception | `RouteToVendors`, `MarkSendFailed` | Same retry jobs |
| 15 | Buyer selection | Buyer replies "1" (automatic); operator `POST /select` is a fallback | — | Unchanged; operator path labelled override | `transaction.Select` | Dashboard labelling only |
| 16 | Transaction | Created automatically on selection, `UNPAID` | — | Unchanged (fulfilment/payment out of scope) | `transaction.Service` | None |
| 17 | Listing publish | Every DRAFT needs operator publish | Lock: auto-publish gated (≥95% of a vendor's last 20 drafts approved unchanged) | Trusted vendors' drafts auto-publish when the gate's evidence holds | `supply` curation service | Flag `AUTO_PUBLISH_TRUSTED_VENDOR_LISTINGS` (default OFF) |
| 18 | Vendor onboarding / activation | Operator | Identity/trust decision | Unchanged (control plane) | `vendor` handlers | None |
| 19 | Discovery batches | Operator creates and sends | By design (no scheduler, 4C) | Unchanged | `distribution` | None |
| 20 | Dashboard | Confirm / Clarify / Route / Associate / Deliver / Select shown as the normal workflow | Phase 3 operator-first UI | Same actions shown as overrides; autonomy metrics, decisions and exceptions visible | `dashboard/app/requests/[id]` | Relabel + autonomy page |
| 21 | Intervention measurement | No way to tell an operator-driven request from an autonomous one (routing writes actor OPERATOR always) | Not needed while everything was manual | Per-workflow classification + manual routing / confirmation rates | events | Decision log + actor-correct events + metrics endpoint |

Feature-gate mechanism found: environment configuration validated at startup
(`internal/config`). There is no separate flag system; the autonomy flags use
the same mechanism.
